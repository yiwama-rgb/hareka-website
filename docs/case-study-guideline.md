# Hareka 事例作成ガイドライン

## このスキルの目的

Harekaの導入事例を作成する際に、毎回同じ説明をしなくて済むよう、ルール・方針・文体をここに集約する。このファイルを読んだClaudeおよびClaude Codeは、以下のガイドラインに従って事例を作成すること。

---

## 1. 読者定義

事例を読む人は以下のいずれか：

- **経営者**（社長・CEO・COO）― CRMの乗り換えや導入を検討している
- **営業責任者・事業部長**― 現場のCRM活用に課題を感じている
- **CRM導入・移行担当者**― 実務を担う人。ある程度ツールの知識はあるが、エンジニアではない

**この人たちに刺さる言葉で書く。エンジニアに向けて書かない。**

---

## 2. 企業情報の匿名化ルール

### 絶対に書かない情報
- 企業名（固有名詞）
- 製品名・サービス名（特定できるもの）
- 代表者名・担当者名

### 書いてよい情報（抽象化した上で）
- 業種（例：「イベント管理SaaS企業」→「BtoB SaaS企業」）
- 従業員規模（例：「営業20〜30名規模」はOK）
- 導入前後のツール名（HubSpot・Salesforceなどのツール名はOK）
- 数値・成果（件数・金額・削減率など、企業特定につながらないものはOK）

### 判断基準
「この情報だけで企業名を検索できるか？」→ できるなら書かない。

---

## 3. 文体・トーン

### 基本方針
- **経営者が読んで「これ、うちの話だ」と思える言葉を使う**
- 技術用語は原則使わない。どうしても必要な場合は一言で完結させ、詳細には踏み込まない
- 数字は積極的に使う（信頼性の証明になる）
- 「すごい技術を使いました」ではなく「お客さんにとって何が変わったか」を前面に出す

### 良い例・悪い例

| 悪い例（テクニカルすぎ） | 良い例（経営者目線） |
|---|---|
| Bulk API 2.0とPythonスクリプトで移行 | 専用ツールでは対応できない規模のため、完全カスタム実装で対応 |
| 3ウェイ数値照合で完全一致を確認 | 移行後に数値の完全一致を独自検証。1件の欠落もなし |
| EmailMessageとTask[Email]の重複問題 | 2系統に分散したメール履歴を整理し、重複ゼロで移行 |
| ステージ別必須プロパティ設定 | 「このステージに進むには入力必須」という営業ルールをHubSpotで再現 |

## 4. 事例の構成テンプレート

以下の順番・見出しで書く。

## 数値ハイライト
（表形式。一番インパクトのある数字を3〜4つ）

## お客様プロフィール
（表形式。業種・規模・移行前後のツール）

## 課題（Before）
（経営者目線の悩み。「あるある」と思える表現で）

## 支援内容
（何をしたか。技術詳細より「判断・工夫・価値」を書く）

## 成果（After）
（数字＋変化した状態。Before→Afterの対比を明確に）

## お客様の声
（実際の言葉。感情の変化が伝わるもの）

## なぜHarekaだったのか
（差別化ポイント。Harekaでないとできなかった理由）

---

## 5. 数字の使い方

数字は信頼性の証明として積極的に使う。ただし文脈なしに数字を並べない。

良い例：
「55万件超のデータを移行。なかでも最も難易度が高かったMRRデータ（34.8億円相当）は、移行後に独自検証で完全一致を確認した。1件の欠落もなかった。」

悪い例：
「総移行件数：55万件。MRR：34.8億円。完全一致率：100%。」

---

## 6. 「なぜHarekaか」の差別化軸

Harekaの強みは以下。事例の中で自然に織り込む：

- SalesforceとHubSpot両方に精通しているから移管がスムーズ
- 代表の岩間が全案件を一貫担当（引き継ぎ・担当変更なし）
- 「ツールを設定して終わり」ではなく顧客が自走できる状態をゴールにしている
- HubSpot Japan CSMとして200社以上を支援した現場知識

---

## 7. Markdownファイルの保存ルール

- 保存先：src/content/cases/
- ファイル名：XX-[会社種別]-[内容].md（例：02-saas-data-migration.md）
- frontmatterの必須項目：title / company / industry / employees / tool_before / tool_after / period / highlight / pubDate / draft / description

---

## 8. 完成チェックリスト

事例を書き終えたら以下を確認する：

- 企業名・製品名・サービス名が特定できる表現がないか
- 技術用語を経営者が理解できる言葉に置き換えたか
- Before/Afterの対比が明確か
- 数字が少なくとも3つ以上含まれているか
- 「なぜHarekaか」が最後に書かれているか
- お客様の声があるか（ない場合は省略可だが、あると強い）
- npm run build でエラーがないか確認したか
