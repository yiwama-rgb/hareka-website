**Data Hub Professional（旧Operations Hub Professional）** が提案されてきた理由は、大きく2つでした。

1. **カスタムコードを使うため**。これが最大の理由です。ワークフローの標準アクションでは届かない処理を、JavaScriptやPythonで書きたい
2. **定期スケジュールでワークフローを回すため**

ところが2026年、この2つがどちらも揺らいでいます。順番に見ていきます。

---

## 1. 理由その1が揺らいだ：エージェントがコードの代わりをし始めた

Agent Hubの登場で、従来のワークフローの標準アクションではできなかったことが、エージェントに仕事をさせることで実現できるようになってきました。

これまでは「標準アクションの一覧にないことをやりたい」となった瞬間、選択肢がカスタムコードしかありませんでした。だから上位プランの契約が必要でした。ところが今は、その"標準アクションの外側"の一部を、エージェントが引き受けられるようになっています。

つまり「コードでしか書けなかったから、そのためにData Hub Professionalが必要だった」という前提が、部分的に崩れているということです。

---

## 2. 理由その2も揺らいだ：定期スケジュールもData Hub Professionalなしで組めた

もう一つの理由だった「定期スケジュール実行」についても、実際に手を動かして確認しました。

筆者が自分のポータルで確認した内容は次のとおりです。

- ポータルの契約は、**Marketing Hub Starter と Sales Hub Professional**。Data Hubは未契約
- **Agent Hub内のワークフロービルダーから、週次スケジュールのトリガーでタスクを作成するワークフローを作成し、公開まで完了した**
- 設定画面に表示されるだけでなく、実際にパブリッシュが通っている

設定項目が画面に出ているだけなら「表示されるが保存できない」というパターンもあり得ます。しかし今回は公開まで通りました。

> なお、HubSpotのナレッジベースには現在も、ワークフローを月次・週次・日次で繰り返す設定にはData Hub Professional以上が必要と記載されています。今後どうなるかは分からない部分が残ります。ただ、現時点で実際にできてしまっているのは事実です。

### 補足：旧ワークフローとAgent Hubの使い分け

ここで、ワークフローを組む場所が2つになったことにも触れておきます。判断の目安は次のとおりです。

- **既存の運用資産を触る** → 旧ワークフローを使う価値がある
- **新しく作る** → まずAgent Hubを検討する
- ただし**Agent Hubで使えるアクションはまだ一部に限られており**、やりたい処理によっては旧ワークフローのほうが向いている
- **旧ワークフローからAgent Hubへの移行は恒久的**で、移行後は元のワークフローツールでは編集できない

整理すると、**旧ワークフローは既存資産の保守用、Agent Hubはこれから組む自動化用**、という住み分けになります。移行が恒久的である以上、既存の仕組みを勢いでAgent Hubに寄せるのは避けたほうが無難です。

## 3. では、月額86,400円は何に払うのか

ここで料金を確認しておきます。HubSpotの公式価格表（hubspot.jp/pricing/data）の数字は次のとおりです。

| プラン | 価格 |
|---|---|
| Data Hub Professional | **年払いで月額86,400円**（月払いは月額96,000円）。コアシート1件を含む |
| Data Hub Enterprise | 月額240,000円 |

提案理由の2本柱が両方揺らいだのだとすれば、この金額は何に対して払うものなのか。ここからが本題です。

先に立場を書いておくと、これは「HubSpotの機能が減った」という話ではありません。**価値の置き場所が変わった**という話です。かつて「コードを書ける権利」に見えていたものが、いま何の権利として意味を持つのか。そこを言語化していきます。

## 4. エージェントとコードの境界線はどこにあるか

この節が本記事の核心です。丁寧に整理します。

一言で言えば、**「自然言語で判断・要約・分類させる」のがエージェント、「プログラムとして厳密に処理させる」のがカスタムコード**です。

### エージェントで十分なこと

- レコードの要約
- 内容の分類
- 優先度の判定
- 下書きの生成
- 複数データを見て「次に何をすべきか」を判断する

つまり、**人が読んで判断していたことをAIに寄せる領域**です。多少の揺れを許容できるなら、こちら側で足ります。人間がやっていた時点でもともと判断にはブレがあったわけで、そこにAIを置くことは、精度面でも運用面でも無理がありません。

### カスタムコードが必要なこと

- 1文字もズレてほしくない
- フォーマットを厳密に固定したい
- エラー時の処理を細かく制御したい
- ロジックを完全に再現したい

エージェントは**「用意された道具の範囲で動く」**ものです。対してカスタムコードは**「コードで処理そのものを自作できる」**。この差が効いてきます。

「たいていは正しい」で困らない業務ならエージェント。「毎回まったく同じでなければ困る」業務ならコード。判断軸はこのひと言に集約されます。

### カスタムコードでなければ厳しい処理、5つの類型

整理すると、次の5つになります。

1. **厳密計算** — 取引条件から社内独自のスコアや料率を計算する
2. **厳密な外部API連携** — 外部システムの仕様に合わせてデータを送る
3. **厳密なデータ整形** — 文字列・日付・番号を業務ルールに沿って整形する
4. **監査可能な分岐ロジック** — 複雑な判定で承認・振り分け・例外処理を自動化する
5. **再現性の高い検証・重複判定** — 複数データを突き合わせて検証・整合性チェックをする

### ただし、3だけでは高い

ここは正直に書きます。

このうち3（厳密なデータ整形）は、電話番号の形式統一や顧客コードの生成といった分かりやすい用途です。イメージしやすいので、提案でもよく例に挙がります。しかし、**これだけのために月額86,400円を払うのは、正直に言って割に合いません。**

元が取りやすいのは、**1（厳密計算）・2（厳密な外部API連携）・4（複雑な判定）・5（検証・整合性チェック）**のような、金額・連携・承認に直結する重い運用を、複数まとめて置き換える場合です。

以下、その具体例を挙げていきます。

## 5. 月額86,400円を回収できる10の事例

ここからは、実際に「元が取れる」形になりやすい使い方を10個挙げます。それぞれ「問題 → なぜエージェントではなくコードか → 元が取れる会社像」の3点で整理します。

### 類型1：厳密計算が必要なケース

#### 事例1：代理店・紹介パートナーへの紹介料を自動計算する

- **問題**：紹介元ごとに料率が違い、さらに初回契約だけ対象、更新は対象外、特定商品は除外、といった条件がある
- **なぜコードか**：この手の料率計算は、AIに判断させるより、契約条件どおりに厳密計算したほうが安全
- **元が取れる会社像**：毎月数十件以上の成約があり、計算ミスが請求トラブルや社内確認工数に直結する会社

#### 事例2：見積・契約の粗利率を自動算出し、基準以下だけ承認に回す

- **問題**：営業が値引きした案件のうち、粗利が一定以下のものだけ承認に回したいが、商品構成や契約期間で計算式が複雑
- **なぜコードか**：厳密計算と複雑分岐の組み合わせ。「粗利率28%未満なら部長承認、20%未満なら役員承認」といったルールはコード向き
- **元が取れる会社像**：値引き件数が多い、または粗利のブレが利益に大きく響く会社

#### 事例3：サブスクの請求開始日・更新日・日割額を自動計算する

- **問題**：契約日、利用開始日、無料期間、月末締め、年契約などが絡んで、請求タイミングや日割額の計算が複雑
- **なぜコードか**：日付処理や金額計算は、毎回同じ式でブレなく算出したい領域
- **元が取れる会社像**：契約形態が複雑で、請求ミスが返金や信用低下につながる会社

### 類型2：監査可能な分岐ロジックが必要なケース

#### 事例4：商談内容に応じて承認経路を自動で変える

- **問題**：金額、商品カテゴリ、顧客区分、支払い条件、契約期間、法務条項の有無などで承認ルートが変わる
- **なぜコードか**：「なんとなく妥当」ではなく、監査可能なルールで100%同じ判定が必要
- **元が取れる会社像**：承認フローが重く、チャットや口頭確認で属人運用になっている会社

#### 事例5：特定条件の顧客だけ、CS・法務・経理へ自動エスカレーションする

- **問題**：「大手企業」「海外取引」「特別条項あり」「未払い履歴あり」「導入期限が近い」など、複数条件で例外対応が必要
- **なぜコードか**：例外条件が多いほど、AIの柔らかい判断より、ルールベースで漏れなく振り分けるほうが強い
- **元が取れる会社像**：案件単価が高く、1件の見落としコストが大きい会社

### 類型3：検証・整合性チェックが必要なケース

#### 事例6：問い合わせや申込データの不備チェックを自動化する

- **問題**：申込フォームや営業入力の内容に抜け漏れがあり、後工程で差し戻しが多い
- **なぜコードか**：「この項目が空ならNG」だけでなく、「契約種別Aならこの3項目必須」「法人なら会社情報必須」といった複合検証が必要
- **元が取れる会社像**：インサイドセールス、審査、契約作成チームが手戻りに追われている会社

#### 事例7：重複リード・重複会社を独自ルールで検出する

- **問題**：メールアドレスの完全一致だけでは足りず、会社名のゆれ、ドメイン一致、電話番号一致、担当者名の近似などを見て重複判定したい
- **なぜコードか**：ルールベースの照合であり、「それっぽい判定」より再現性が大事
- **元が取れる会社像**：広告・展示会・複数フォームからリード流入があり、重複が営業効率を下げている会社

#### 事例8：受注前に「既存契約・未払い・サポート事故」を横断チェックする

- **問題**：新しい商談を進める前に、既存契約、未払い請求、重大なサポート案件、過去の解約などをまとめて確認したい
- **なぜコードか**：AIに要約させることはできても、「この条件に当てはまるなら必ず止める」はコードのほうが強い
- **元が取れる会社像**：営業・CS・請求が分かれていて、情報分断による事故受注が起きている会社

#### 事例9：外部システムへ渡す前の検証ゲートを作る

- **問題**：HubSpotのデータをそのまま送ると、項目不足・形式不一致・コード不正で連携エラーになる
- **なぜコードか**：カスタムコードやWebhookはHubSpotの外までワークフローを拡張できる。その前段で送信可否を厳密判定できるのが大きい
- **元が取れる会社像**：外部システム連携の失敗が、出荷遅延や請求漏れに直結する会社

#### 事例10：営業やマーケの入力データを定期監査し、異常値だけ自動修正・通知する

- **問題**：担当者ごとに入力品質が違い、国コード、部署名、流入元、ステージ、担当者情報などが崩れてレポートが信用できない
- **なぜコードか**：単純な整形だけでなく、異常値検出 → 補正 → 直せないものだけ通知、まで組むなら投資対象になる
- **元が取れる会社像**：レポートの精度が経営判断や広告投資判断に影響する会社

## 6. どういう会社なら本当に元が取れるか

率直に書きます。次のどれかに当てはまらないと、高く感じやすいはずです。

- 1件の計算ミスや承認漏れが、**数万円〜数十万円の損失**になる
- 月に**何十件〜何百件**も同じ判定・検証をしている
- **2〜3人以上**が毎週同じ確認作業をしている
- データ不整合が営業・請求・CSの事故につながっている
- 外部システム連携のエラー修正に継続的な工数がかかっている

逆に言えば、「便利そうだから」というレベルでは元は取りにくい、ということです。

実務上の整理は次のようになります。

| 自社の状況 | 判断 |
|---|---|
| データ整形だけが目的 | 高いと感じやすい |
| 厳密計算・外部API連携・複雑な判定・整合性チェックのような重い運用を複数まとめて置き換える | 元を取りやすい |
| AIで代替できる曖昧な業務が中心 | Data Hub Professionalは不要寄り |
| 数式・監査・整合性・例外処理・外部連携が中心 | 価値が出やすい |

契約を続けるか迷っている場合も、これから提案する場合も、見るべきはこの表の左側です。**「カスタムコードが使えるかどうか」ではなく、「厳密さを要求される業務が、いくつ・どれだけの頻度であるか」**が判断材料になります。

## よくある質問（FAQ）

### Q. Data Hub Professionalを解約しても、今動いているワークフローは残りますか？

A. 上位プラン専用の機能を使ったワークフローは、動作しなくなる可能性があります。特に、カスタムコードアクションやスケジュールトリガーを含むものは注意が必要です。解約前に、どのワークフローがどの機能に依存しているかを棚卸しすることをおすすめします。ポータルごとに構成が異なるため、断定はできません。実際の挙動は必ず事前に確認してください。

### Q. カスタムコードの代わりに、エージェントをどこまで使えますか？

A. 要約・分類・優先度判定・下書き生成であれば置き換えられます。一方、厳密計算、外部APIとの仕様通りの接続、監査可能な分岐、再現性の高い検証は、まだコードの領域です。判断軸はシンプルで、**「同じ入力に毎回同じ答えが返る必要があるか」**。必要ならコード、許容できるならエージェントです。

### Q. Agent Hubのワークフローで、従来型ワークフローを完全に置き換えられますか？

A. 現時点では不可です。Agent Hubで使えるアクションはまだ一部に限られています。また、旧ワークフローからAgent Hubへの移行は恒久的で、移行後は元のワークフローツールでは編集できません。既存資産は旧ワークフローで保守し、新規はAgent Hubで組む、という使い分けが現実的です。

### Q. Data Hub Professionalは、旧Operations Hub Professionalと同じものですか？

A. 同じ製品です。HubSpotが名称を変更したものです。以前の資料や社内ドキュメントに「Operations Hub Professional」と書かれていても、指しているものは同じと考えて差し支えありません。

## まとめ：払う理由が変わった

Data Hub Professionalは、かつて**「コードを書くため」「定期実行するため」**のライセンスでした。その2つは、AIに侵食されました。エージェントが標準アクションの外側を埋め始め、定期スケジュールも上位プランなしで組めてしまう場面が出てきています。

では価値がなくなったのかというと、そうではありません。**価値の置き場所が変わった**のです。

いま残っているのは、**「AIで賢くやるため」ではなく、「売上・請求・承認・データ品質を、厳密ルールで事故なく回すため」に払うライセンス**です。

- 曖昧でいい業務は、エージェントへ
- 1円もズレてはいけない業務は、コードへ

この線引きができた会社にとって、月額86,400円は妥当な投資になります。逆に、線引きをしないまま「カスタムコードが使えるから」という理由で契約し続けているなら、一度棚卸しをする価値があります。
